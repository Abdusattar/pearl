# 07. Экран «Купили» — план первого кода нового входа `/new`

> 16.09.2026. Основание: макет версии 7, блок 2 (2б форма, 2в карточка),
> 3г (единица, фасовка, уровень по категории), решения владельца 14–15.09.
> Статус: план на утверждение, кода нет.

## Что строим в первом шаге

Одна форма `GET/POST /new/buy` и карточка покупки `GET /new/buy/{id}`
(чтобы после «Записать» было куда попасть и что убрать). Лента 2а — следующим
шагом, отдельно.

Что из 2б входит сразу:

| Часть формы | В первом шаге |
|---|---|
| «У кого?» — чипы поставщиков по частоте за 60 дней + «Кто-то другой» (поиск / новый) | да |
| Список с прошлого привоза этого поставщика (кол-во, цена) | да |
| Строка товара: подсказка из каталога, единица из карточки текстом | да |
| Фасовка: «2 лотка» → в единицу карточки | да (лягушка) |
| Новый товар в строке: сначала похожий, потом категория + единица | да |
| Вопрос о цене (×2 от медианы) с чипами «Да» / «Поправлю» | да (уже есть `price_check`) |
| Вопрос о повторе (поставщик + сумма или набор позиций за 10 дней) | да |
| «Для кого»: Общее / Школа / Садик; при одном ремонте — обязателен | да |
| Дата: сегодня / другой день | да |
| Оплата: в долг / из кассы (карман) / со счёта (садика · школы) / часть / учредитель | да |
| Фото чека приложить | да, как файл к покупке |
| Фото → строки заполняются распознаванием | **нет, второй шаг** (путь OCR есть, подключим после того, как форма руками устоится) |

## Данные: добавки рядом со старыми таблицами

Старые таблицы остаются источником правды, старый вход видит всё, что
заведено новым (проводки, приходы, долг). Новых сущностей одна.

**Новая таблица `purchases`** — шапка покупки, «одна покупка = одна строка»:
поставщик, площадка (site org), дата, итог, способ оплаты
(`debt|cash|account|part|founder`), оплачено, карман (`paid_from_user_id`),
счёт (`account_org_id`), для кого (`allocation`: `shared|org_id`), фото
(`receipt_id`), кто и когда завёл, `deleted_at`, `dup_confirmed`.

**Новые колонки:**
- `transactions.purchase_id` — проводки по категориям (как режет
  `create_split_transactions`) остаются, но смотрят на одну шапку. Так лента
  старого входа и юнит-экономика не меняются, а новая лента показывает одну
  строку.
- `transactions.paid_from_user_id` — карман плательщика. Понадобится и
  «Расходу без чека», и зарплате из кармана Айжан; новая Касса считает
  карманы отсюда плюс `cash_fundings.accountable_user_id`.
- `transactions.account_org_id` — со счёта какого объекта (при
  `paid_directly=True`).
- `products.pack_name`, `products.pack_qty` — фасовка («лоток», 30).

**«Заплатил учредитель»** — без новых полей: `CashFunding(source_founder_id,
accountable_user_id=учредитель)` + проводка с `paid_from_user_id=учредитель`.
Карман учредителя в нуле, в кассе видно взнос и расход.

**Склад.** Приход `WarehouseReceipt` пишется по каждой строке, как сейчас:
это история цен для проверки и себестоимость. Мелочь от основного отличает
новый экран Склада по `product_categories.level` — показывает остаток только
основным. Старый склад продолжает показывать всё, как показывал.

## Правила формы

- Итог = сумма строк, отдельного поля суммы нет.
- Единица не вводится. Если у товара есть фасовка, рядом с количеством выбор
  «кг · мешок 25 кг»; сервер переводит в единицу карточки, хранит в ней.
- Чужая единица → ошибка строки, не правка карточки (как в старой форме).
- Новая карточка рождается только здесь: похожий (`rank_candidates`) →
  «Да, он» / «Новый товар: категория, единица». Уровень от категории.
- Вопрос о цене и вопрос о повторе — обе проверки на сервере, форма
  возвращается со всеми строками и вопросом; запись только после ответа.
  Ничего не коммитится до ответа.
- Повтор: тот же поставщик за 10 дней и (та же сумма или тот же набор
  `product_id`); либо тот же `file_hash` фото. Ответ «да, другой» пишет
  `dup_confirmed`.
- «Для кого»: по умолчанию Общее. Если все строки из категорий «ремонт» или
  «стройматериалы» — чип пустой, форма спрашивает.
- Оплата по умолчанию: у поставщика с долгом — «в долг», у Рынка — «из
  кассы» (правило: был ли у поставщика хоть один закуп в долг за 60 дней).
- «Из кассы» — карман вводящего; «платил другой» открывает выбор Махабат /
  Мунара / Айжан.
- «Со счёта» — выбор садика или школы обязателен.
- Дата события, не записи.

## Где живёт код

- `app/routers/new_buy.py`, префикс `/new` (свой роутер, своя навигация).
- `app/templates/new/base.html` — каркас нового входа (пять пунктов:
  Сегодня, Расходы, Склад, Касса, Дети; пока живые ссылки только на то, что
  есть), `new/buy.html`, `new/purchase.html`.
- `app/services/purchases.py` — `suggest_suppliers`, `prefill_from_last`,
  `find_duplicate`, `record_purchase`, `remove_purchase`. Переиспользует
  `resolve_item_product`, `price_anomaly_hint`, `create_split_transactions`,
  `create_warehouse_receipts` (вынести из роутера в сервис, старый вход
  импортирует оттуда).
- Миграция одна: таблица + пять колонок, данных не трогает.
- Доступ: те же роли, что у `/expenses/add`; площадка = `site_org_id` объекта
  пользователя (Махабат → 4, Айжан → 4).

## Проверки перед показом

- Тесты `tests/test_new_buy.py`: подстановка с прошлого раза; единица из
  карточки и отказ чужой; фасовка «2 лотка» → 60 шт по цене за шт; вопрос о
  цене; вопрос о повторе и «да, другой»; пять способов оплаты → проводки,
  карман, счёт, взнос учредителя; ремонт без «для кого» → вопрос; долг
  поставщику после записи; убрать покупку откатывает склад и долг.
- Живой прогон на локальной базе в браузере: Халима с прошлого списка,
  Рынок с пустыми строками, новый товар «сечка».
- Стандарты интерфейса макета: поля 16 px, тап-зоны 44 px, вопрос отдельной
  строкой с чипами, «Записать» одно на форму, опасное тише и справа.

## Что не входит и почему

- OCR-заполнение с фото и бот 1б — после того, как форма руками поживёт.
- Лента 2а, оплата поставщику 2в «Оплатить», «Поправить» — следующие шаги
  (правка через «убрать и завести заново» в первом шаге — временно).
- Новый экран Склада и Касса с карманами — свои блоки.

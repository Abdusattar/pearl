# OCR — история выбора решения

> Обновлено: 2026-07-05

## Задача

Распознавание фото квитанций (хозяйственные расходы школы и садика):
- Рукописные квитанции (большинство)
- Печатные чеки
- Фото с телефона (разное освещение, качество)
- 92 накопленных фото у Мунары в media/receipts/

## Эволюция выбора

### 1. Google Cloud Vision (первоначальный план, ~май 2026)
- 1000 запросов/мес бесплатно
- Отклонён: непонятна стоимость сверх лимита, привязка к Google Cloud

### 2. EasyOCR (локальный)
- Попытка: локальное решение без API
- Отклонён: качество на рукописях неприемлемое, тяжёлый для VPS

### 3. OpenRouter Vision — qwen/qwen2.5-vl-7b-instruct:free (история)
- Бесплатно, работает через OpenRouter API, неплохо на печатных
- Минус: **на рукописях не справляется** — критично для наших квитанций

### 4. OpenRouter Vision — google/gemini-2.5-flash-lite (текущий, с 19.06)
- **Статус: в продакшне** — `app/services/ocr.py` и `app/services/normalize.py`
- $0.10 / $0.40 за 1M токенов (вход/выход), 1M контекст
- На рукописях справляется заметно лучше, чем qwen2.5-vl-7b:free

## Тест 05.07 — китайские vision-модели как альтернатива

Повод: жалоба на скорость прода потянула за собой вопрос «а нет ли модели
сопоставимой по цене, но лучше именно на рукописных чеках». Прогнали на двух
реальных чеках (один чёткий, один почти нечитаемый даже для человека):

| Модель | Цена вх/вых за 1M | Итог теста |
|---|---|---|
| **google/gemini-2.5-flash-lite** (текущая) | $0.10 / $0.40 | На чётком чеке — 100% верно (все позиции, количества, итог). На грязном — нестабильно (в одном прогоне частичный null, в другом галлюцинация числа) |
| qwen/qwen3-vl-32b-instruct | $0.104 / $0.416 (сопоставимо) | На чётком чеке хуже: исказил названия («керточина» вместо картошка), ошибся в qty (48 вместо 78). На грязном — числа правдоподобнее Gemini, но названия тоже не разобрал |
| z-ai/glm-4.5v | $0.60 / $1.80 (дороже в 4-6 раз) | Провал: на грязном чеке пустой ответ (`content: None`), на чётком — ответ обрезался на `max_tokens=2048` посреди JSON (модель «thinking»-типа, тратит бюджет на рассуждение до финального ответа) |

**Решение: остаться на Gemini 2.5 Flash Lite.** Ни один кандидат не показал
превосходства ни по цене, ни по качеству на этих образцах. GLM-4.5V для
честного теста потребовал бы больший `max_tokens` (и тогда реальная цена
запроса выше заявленной). Скрипт сравнения — в scratchpad сессии, не в
репозитории; при повторном тесте: та же image_url структура запроса, что и
в `ocr.py`, просто менять `model` в payload.

**Вывод про методологию:** 2 чека — маленькая выборка, температура 0.1 даёт
разброс между прогонами одной и той же модели. Если будет ещё повод менять
модель — тестировать на 15-20 чеках с посчитанным % расхождений, не на паре
примеров.

## Архитектура OCR пайплайна

```
Фото → OpenRouter Vision API → JSON позиций → receipt_items в БД → confirm страница (Мунара правит)
```

Мунара **подтверждает** каждую квитанцию на confirm-странице перед сохранением.
Это страхует от ошибок OCR — человек в контуре.

## Что реализовано

- Upload страница с OCR overlay (индикатор прогресса)
- Confirm страница: редактирование позиций, пересчёт qty→итог
- file_hash дедупликация (повторная загрузка того же фото не создаёт дубль)
- Ручная запись без квитанции (если фото нет)

## Распознавание — вспомогательный путь, не главный (14.09.2026)

Владелец: «не скажу, что списание через фото чеков прям классно работает».
Прод за 30 дней: 94 чека, распознавание использовано в 23, 71 введён руками;
мясо, молоко, хлеб без фото ни разу; треть чеков переделывается (56 правок
на 92). Пять постоянных поставщиков дают две трети денег повторяющимися
позициями.

Решение в рамках ревизии: главный путь ввода — «привоз от поставщика» с
позициями и ценами с прошлого раза; рынок — быстрая форма с подсказкой
товара; лист кухни — «как вчера» с правкой количеств. Фото прикладывается
как документ по желанию, распознавание только предзаполняет и никогда не
решает. См. [[architecture/revision_2026_09]].

## Единый конвейер (16.09.2026)

Решение владельца: одно распознавание на чек, лист кухни и лист
пересчёта; разница только в контексте. `app/services/recognize.py`:

1. Один вызов модели с картинкой **и списком ожидаемых товаров** (id, имя,
   единица, обычная цена, фасовка): у чека — что этот поставщик привозил за
   90 дней и частые покупки площадки; у листа кухни — вчерашний лист,
   остатки, зелень и специи; у пересчёта — весь основной склад. Чтение
   почерка становится выбором из 20–90 вариантов.
2. Сведение чисел без ИИ: количество × цена = сумма; при расхождении сдвиг
   запятой, обмен местами, вывод цены или количества из суммы, если
   результат рядом с обычной ценой. Реальные случаи: картошка 12,61 → 126,1;
   филе «1 × 24 = 365» → 24 × 365 (по обычной цене).
3. Единицы в единицу карточки: г↔кг, мл↔л, фасовка (лоток → шт).
4. Нечёткий поиск по каталогу как запасной путь: точное имя или почти
   полное совпадение — подставить; «мел» ≠ «Мелисса», «Луг» ≠ «Лук» —
   вопрос. Строки из одних цифр (итоги) отбрасываются.
5. Терпимый разбор JSON: висячие запятые, одинарные кавычки, текст вокруг.

**Оценка на 28 фото-чеках прода, 193 строки Махабат** (скрипт в scratchpad
сессии 16.09, фото прода скачаны туда же):

| Разбор | Товар | Кол-во | Цена | Сумма строки |
|---|---|---|---|---|
| Старый (два вызова, flash-lite) | 51 % | 46 % | 44 % | 46 % |
| Новый, flash-lite | 77 % | 67 % | 65 % | 67 % |
| Новый, gemini-2.5-flash | 79 % | 73 % | 73 % | 72 % |

Pro остановлен владельцем как слишком медленный. **Модель по умолчанию —
gemini-2.5-flash** (`OCR_MODEL`), ~3,2 тыс. токенов на фото. На реальном
листе кухни 10.09 flash разобрал 17 из 17 строк («500г + 3,500» → 4 кг,
«300г − 810г» → 1,11 л), lite читал латиницу. Оставшиеся промахи —
рыночная канцелярия, которой нет в списке ожидаемых и которая почерком не
читается; они уходят человеку вопросом, не молча. Кнопки: «Заполнить с
фото» в Купили, «Разобрать фото» в Листе кухни.

## Текст тем же конвейером (23.09.2026)

Остаток и передачу пишут и текстом («остаток склада на сегодня молоко 80л, …»):
`recognize.recognize_text` — тот же промпт с каталогом склада, без картинки. Арифметика
в строке («25кг + 5кг = 30кг», «750*7=5,250гр») → итог; «7,700» без единицы — десятичная
в единице карточки. Повтор товара ниже — уточнение, побеждает последняя строка. Модель
получает и выученные слова товара («also written as: томат»). Ошибки 23.09 на 33
строках: томат → помидоры, «0,2 гр» → 0 кг, 3 уточнения как отдельные строки — ловит
только подтверждение человеком. Модель остаётся Gemini 2.5 Flash (владелец 23.09).

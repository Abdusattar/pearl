# Модуль биллинга (долги/переплаты)

> Зафиксировано: 2026-07-03

## Ключевое ограничение, определившее архитектуру

Протокол банка (Optima, OSMP/QIWI) не передаёт назначение платежа — родитель
вводит PIN и платит сумму, без выбора «за что» (учёба/проезд/секция). Значит
система в принципе не может узнать, за какую конкретно услугу пришли деньги.

## PIN — тестовые фикстуры банка не сдвигают реальную последовательность (найдено 16.07)

`get_next_free_pin()` берёт `MAX` по всем `Student.pin` — включая постоянные фиктивные
PIN 9001/9002, заведённые для тестов Optima (см. раздел про них ниже). Реальный новый
ребёнок получал бы 9003 вместо следующего свободного (0097), пока их не исключили из
подсчёта через `TEST_PIN_THRESHOLD = 9000` (`app/services/students.py`). Урок: любая
"постоянная тестовая запись" в таблице, по которой считается MAX/COUNT для реальной
последовательности — кандидат на подобный баг, проверять при заведении новых фикстур.

## Массовая правка дат/групп/статуса — `/students/bulk-dates` (16.07)

Одноразовый бэкфилл: у 78 из 79 активных детей `Enrollment.start_date` — техническая
дата миграции (03.07.2026), не реальная дата поступления. Дата САМА ПО СЕБЕ не влияет
на начисления задним числом (пропорция срабатывает только если дата попадает в текущий
расчётный месяц) — значение этого поля для существующих детей чисто историческое, не
денежное. Статус (Активен/Заморожен/Выбыл), наоборот, влияет на начисления сразу — это
приоритет при заполнении. Функция `set_first_enrollment_start()` правит именно самую
раннюю запись `Enrollment` — ту же, что читает `_proration_factor()` в биллинге; писать
в любую другую запись значило бы разойтись с тем, что реально влияет на начисление.

**Решение: один общий баланс на ребёнка**, а не раздельный учёт по видам услуг.
Альтернативой было бы завести отдельный PIN на каждую услугу — отклонено, это
усложнило бы жизнь родителю (несколько кодов) ради выгоды, которая не нужна
школе на практике.

## Модель данных

- **Учёба** — **переделано 13.07** (было `Student.extra.monthly_fee`,
  индивидуальное число на каждого ребёнка — см. раздел ниже про то, почему
  это оказалось неверной моделью). Теперь: `Service` с флагом `is_tuition=True`
  (одна такая услуга на объект, цена = базовый тариф, редактируется на
  `/services/` как у любой услуги, применяется автоматически всем активным
  детям объекта — не через чекбокс) + `Student.discount_amount` (скидка в
  сомах персонально ребёнку, не процент). Эффективный тариф = цена
  `is_tuition`-услуги минус `discount_amount`, посчитано в
  `services/billing.py::_tuition_fee()`.
- **`Service`** — справочник услуг с ценой, привязан к `organization_id`
  (цена может отличаться школа/садик). Два вида: `is_tuition=True` (ровно
  одна на объект, обязательная для всех, без чекбокса, удаление
  заблокировано на сервере) и обычные опциональные (проезд, секции —
  подключаются по ребёнку через `StudentService`)
- **`StudentService`** — подключение услуги ребёнку, с историей (`start_date`/
  `end_date`, тот же паттерн что `Enrollment` для групп) — включил/выключил
  чекбоксом на карточке ребёнка
- **`Charge`** — начисление: `student_id`, `amount`, `description`, `date`.
  Единственный источник — автоматическое начисление раз в месяц, сумма = тариф
  + все активные `StudentService`. **Ручной корректировки (произвольная
  сумма+описание вручную) в системе нет — убрана целиком 04.07**, см. ниже.
- **Баланс** = `сумма(Charge)` − `сумма(Transaction where type=income)` по
  `student_id`. Положительное = долг, отрицательное = переплата

## Генерация начислений — без cron

`generate_monthly_charges()` в `app/services/billing.py` вызывается при каждом
заходе на `/students/` или `/reports/` — идемпотентно (проверяет, есть ли уже
начисление за этот месяц по `description == "Начисление за месяц"`). Тот же
паттерн, что и авто-архивация выбывших студентов (`archive_stale_students`) —
никакого планировщика/cron не требуется для простых периодических задач в
этом проекте, достаточно проверки на чтении.

## Структура интерфейса (IA) — обновлено 04.07

Изначально баланс и тариф были прямо в списке `/students/` — пользователь
справедливо указал, что это превращает список в свалку цифр. Дальше принцип
«у каждого вида данных — одно чёткое место» довели до уровня отдельных
страниц/форм, не только списка:

| Место | Что показывает |
|---|---|
| `/students/` | Только личные данные: PIN, ФИО, группа, статус (+фильтр по группе/статусу). Вся строка кликабельна → карточка |
| `/students/{id}/edit` (карточка) | Два независимых блока с раздельным сохранением: «Личные данные» (ФИО по частям, группа, статус, контакты родителя) и «Оплата» (тариф, доп.услуги). Денег и истории здесь больше нет |
| `/students/{id}/history` | Баланс + единая хронологическая лента начислений и оплат (цвет/знак различает начисление vs оплату, бейдж Optima/Вручную у оплат) |
| `/reports/` | Сводный долг/переплата по ВСЕМ детям — фильтр по группе + чекбокс «Только с долгом», итоговые суммы сверху |
| `/income/` (Оплаты) | Список платежей с колонкой текущего баланса ребёнка; клик по строке → `/history` |

**Важный паттерн, введённый 04.07 — просмотр/редактирование как отдельные
режимы.** И «Личные данные», и «Оплата» на карточке по умолчанию открываются
как текст (не поля ввода) — кнопка «Изменить» переводит в редактируемый режим,
«Сохранить» спрашивает подтверждение, «Отмена» откатывает без запроса на
сервер. Причина: Айжан и Мунара нетехнические, боятся случайно испортить
данные — редактирование должно быть осознанным действием, не побочным
эффектом открытия страницы. Использовать этот же паттерн для будущих форм
редактирования данных, которые правятся редко, но просматриваются часто.

## Ручная корректировка — убрана целиком (04.07)

Была форма «добавить начисление» с произвольной суммой (+ долг / − списание)
и текстовым описанием — для старых долгов и разовых скидок. Убрана по
инициативе владельца: эндпоинт был доступен любому залогиненному пользователю
без ограничения роли, а у `Charge` не было `created_by` — то есть кто угодно
мог списать долг ребёнку без единого следа, кто это сделал. Решение — не
чинить (роль+аудит), а убрать функцию целиком. Если понадобится занести
старый долг/скидку — сейчас в системе для этого штатного механизма нет.

## Статус ребёнка "Заморожен" — реализовано 16.07

Родитель договаривается на паузу (месяц-два), место в группе остаётся за
ребёнком — не отдаётся другому. Экономика (объяснено Абдусаттаром 16.07):
если место не резервировать, его займёт другой ребёнок и школа заработает
на нём полную сумму — значит 50% (не 0%, не 100%) это компромисс за
удержание места. "Бронь" и "Заморожен" — один и тот же механизм под
разными словами (подтверждено 16.07), не два статуса.

Пока актуально **только для Садика Сокулук** (подтверждено Махабат
16.07) — Школа и Кожомкул, возможно, вообще не будут им пользоваться,
возможно позже понадобится что-то своё. `Student.status` — обычная
строка без CHECK-constraint в БД, так что добавить ещё один статус
для них позже, если появится конкретный запрос — не переделка, а просто
новое значение.

**Модель:** `Organization.frozen_discount_percent` (Numeric, default 50)
— настройка объекта, не константа в коде: софт планируется другим
садикам/школам, у каждого объекта могут быть свои цифры (или этот статус
вообще не использоваться). Редактируется на `/services/` теми же, кто
меняет тариф (`PRICE_EDITORS` — Айдай/Талас), через
`POST /services/frozen-percent`.

**Начисление** (`billing.generate_monthly_charges`): при `status=='frozen'`
— `tuition_fee * frozen_discount_percent / 100`, без доп.услуг (ребёнок
ими не пользуется), без пропорции по дате (упрощение — заморозка средины
месяца не пересчитывается по дням).

**Enrollment НЕ закрывается** при заморозке (`update_student` — ветка
`status == "frozen": pass`, ничего не трогает) — место в группе остаётся
занятым за ребёнком, в отличие от `inactive`, где Enrollment закрывается.

**Optima** (`optima.py`): `status not in ("active", "frozen")` → отказ —
заморожённый ребёнок должен иметь возможность оплатить свои 50% через банк
тем же PIN.

**Отчёт должников** (`reports.py`) включает `frozen` наравне с `active` —
у заморожённого ребёнка тоже может быть долг.

**Месяц самой заморозки не пересчитывается** (идемпотентность
`generate_monthly_charges` по месяцу) — скидка начинает действовать
только со следующего начисления. Осознанно принято 16.07: возвращать
ручную корректировку начислений (убрана 04.07 из-за отсутствия аудита)
ради разовой переплаты за один месяц — дороже, чем сама проблема.
Решение с родителем в такой месяц — устно, вне системы.

## Скидка за дни отсутствия — решено 10.07, не реализовано

Вопрос висел с 08.07 (см. [[architecture/warehouse_module]], гап-анализ
09.07 — «Корзина B»). Ответ Мунары: **перерасчёт минус 100 сом за каждый
день пропуска**, фиксированная сумма, не пропорционально тарифу.

Источник дней пропуска — уже готовый `Attendance` (09.07, `present=False`).
Реализация ещё не спроектирована — открытые вопросы для отдельного
блюпринта: считать ли по всем детям одинаково 100 сом, или учитывать, что у
части детей другой тариф; входит ли перерасчёт в `Charge` при генерации
(значит `generate_monthly_charges()` должен читать `Attendance` за период),
или это отдельная сущность-корректировка (но ручная корректировка была
убрана целиком 04.07 из-за отсутствия аудита — если возвращать что-то
похожее, обязательно с `created_by` и не давать произвольную сумму, только
детерминированный расчёт от `Attendance`).

## Тариф — реальная услуга + скидка в сомах (13.07, была свободным числом)

**Как обнаружилось:** `Student.extra.monthly_fee` изначально задумывался как
«индивидуальный тариф на ребёнка», но по факту у 96 детей Сокулука было
всего 5 значений (8000×40, 7500×28, 5000×6, 5500×2, 4000×8) + 12 детей
вообще без тарифа. Абдусаттар подтвердил реальную механику: 8000 — базовый
тариф по умолчанию для всех, отклонения — это **скидка в сомах**
конкретному ребёнку (500/3000/2500/4000 соответственно), не другой тариф и
не проценты.

**Почему не подошёл уже существующий `discount_percent`:** заведён 12.07
специально под скидку на тариф, но (а) процентный, а не в сомах, (б) форма
карточки ребёнка ни разу не получила полей ввода для него — заготовка на
сервере была, ввести скидку через UI было физически нельзя. Отсюда 0 у всех
96 детей на момент обнаружения — не «скидок нет», а «поле было
недоступно».

**Почему тариф стал `Service`, не константой в коде:** тариф будет расти
(подтверждено), и менять его нужно обычной правкой цены на `/services/`, не
деплоем кода. `is_tuition=True` — единственный маркер, по объекту, а не по
имени строки (в отличие от `SERVICE_CAT_NAMES`/`RECURRING_ONLY_NAMES` в
`expenses.py`, оба — известный техдолг, здесь сознательно сделано через
явный флаг).

**Миграция существующих данных** (`p6q7r8s9t0u1`, `q7r8s9t0u1v2`):
`discount_amount = 8000 - monthly_fee` для тех, у кого тариф был, `0` для
12 без тарифа (раньше они не получали начисление вообще —
`_tuition_fee() == 0` → `total <= 0` → `generate_monthly_charges()`
пропускал их молча). Проверено на реальных 96 детях после пересчёта —
распределение начислений совпало с исходным один в один, никого не задело
задним числом.

## Переходный тариф — от разового снимка к динамическому расчёту (22.07)

**Задача:** при повышении базового тарифа (8000 → 10000) дети, зачисленные
до определённой даты, должны какое-то время продолжать платить старую цену
(«переходный период»), пока не переведутся все на новую с конкретной даты.

**Первая версия (снимок) и почему её пришлось переделать.** Изначально
кнопка «Зафиксировать» на `/services/` разом проставляла
`Student.legacy_tariff_amount` всем активным детям, чья дата поступления на
тот момент была раньше границы. Проблема всплыла в тот же день дважды:
(1) если сначала повысить `Service.price`, а потом нажать «Зафиксировать» —
снимок брал уже НОВУЮ цену, а не старую (порядок действий имел значение и
один раз реально был перепутан на проде); (2) если поправить дату
поступления ребёнка ПОСЛЕ снимка (частый случай — Махабат донабирает
реальные даты вместо технической даты миграции), снимок не обновлялся без
повторного клика — то есть корректность зависела от точного порядка
действий человека, а не от факта в данных.

**Итоговая модель — полностью динамический расчёт, без снимка на
ребёнке.** `Organization.legacy_tariff_cutoff` (граница даты поступления),
`legacy_tariff_price` (цена для старых — отдельно от `Service.price`,
именно поэтому повышение цены больше не может «затереть» историческую
цену) и `legacy_tariff_until` (когда период заканчивается) — три постоянных
поля объекта, не разовое действие. `billing._tuition_fee()` при каждом
начислении сам решает базу: если сегодня ≤ `legacy_tariff_until` и ребёнок
непрерывно зачислен раньше `legacy_tariff_cutoff` — берёт `legacy_tariff_price`,
иначе обычную `Service.price`. Поправить дату поступления или саму границу
можно в любой момент до следующего начисления — пересчитывать вручную
нечего, корректность следует из данных на момент начисления, а не из
порядка кликов.

**Ключевой нюанс — «непрерывность», не «первая когда-либо дата».**
`billing.continuous_enrollment_since()` идёт по `Enrollment` ребёнка от
самой свежей записи назад и останавливается на первом настоящем разрыве
(`end_date` одной записи раньше `start_date` следующей — перевод между
группами день-в-день разрывом не считается). Это было осознанное решение
через explicit-вопрос владельцу: ребёнок, который был «старым», потом
выбыл и вернулся уже ПОСЛЕ границы цены, не должен получить старую цену
просто по факту давней первой даты поступления — платит новую цену сразу
(выбор владельца, вариант «по дате + непрерывность», не «просто по дате»).
Наивный `MIN(Enrollment.start_date)` (как в `_proration_factor`, для другой
задачи это нормально) здесь дал бы неверный результат.

**Для страниц со списком детей** (`/students/bulk-dates`) есть версия той
же функции без запроса на каждого ребёнка —
`continuous_since_from_enrollments()` принимает уже загруженный список
`Enrollment` (тот же принцип, что уже применялся для фикса N+1 в
`bulk_dates_save`). Там же показывается бейдж «сколько будет платить»
каждому ребёнку — реальная сумма (база минус `discount_amount`, та же
формула, что `_tuition_fee()`, вынесена в `tuition_base_price()`), с
пометкой «(до ДД.ММ)» у временной цены, чтобы её не приняли за постоянную.

**Реальный баг, найденный при проверке (22.07):** карточка ребёнка
(`/students/{id}/edit`) считала «Тариф за учёбу» отдельным дублирующим
кодом прямо из `Service.price`, вообще не зная о переходном тарифе — живая
проверка на реальных двух детях на старой цене показала 10000 вместо
верных 8000/7500, хотя настоящее начисление в конце месяца уже считало
правильно. Урок: `_tuition_fee()`/`tuition_base_price()` — единственный
источник истины про тариф ребёнка, любой другой код, который отображает
«сколько платит», обязан звать именно её, не дублировать логику инлайн.

**Разработка** через explicit-вопросы владельцу на каждом развилке (не
молча реализовывать первый пришедший в голову вариант) — единая дата
границы на весь объект (не по ребёнку), уже начисленные месяцы не
пересчитываются задним числом (действует только вперёд), возврат после
выбытия — по новой цене. Архитектурный выбор снимок→вычисление обсуждался
через advisor: отвергнут более простой вариант «переиспользовать
`discount_amount`» — 44 ребёнка на объекте уже имеют реальные персональные
скидки по другим причинам (многодетность и т.п.), совмещать в одном поле
означало бы терять источник скидки или удваивать её смысл.

## Колонка «Оплата (месяц)» в списке `/students/` (23.07)

По запросу — в списке детей рядом со статусом видно итоговое начисление за
текущий месяц на каждого ребёнка. Намеренно **не пересчитывается заново** —
берётся уже существующая запись `Charge` за текущий период
(`description == "Начисление за месяц"`), которую `generate_monthly_charges()`
и так гарантированно создаёт при каждом заходе на `/students/` (вызывается в
начале того же обработчика). Один batch-запрос на всех видимых детей, без
N+1. Это тот же принцип «единственный источник истины», что и выше про
`tuition_base_price()` — колонка показывает **фактическую** сумму (легаси-
тариф, скидка, заморозка%, пропорция за неполный месяц, допуслуги), а не
голый тариф без поправок.

## Инцидент 04.08 — гонка задвоила начисления 50 детям на 1.6млн сом

`generate_monthly_charges()` (см. раздел выше «без cron») проверяет «уже
начислено за этот месяц?» и вставляет начисление без блокировки между
проверкой и записью — классический TOCTOU. 1 августа в 16:35 пять запросов
подряд за 24 секунды (видимо, несколько открытых вкладок/переходов между
`/students/` и `/reports/` одновременно) — транзакция каждого достаточно
долгая (перебирает всех активных детей объекта), чтобы все пять успели
проверить «не начислено» до того, как предыдущий закоммитил. Итог: 50 из
60 детей с начислениями получили по 5 одинаковых копий начисления за
август вместо одной — 1 612 000 сом фантомного долга, реальных денег
никто не платил и не собирал (`Transaction` не затронут).

**Диагностика через прод (read-only, `railway variables --service Postgres
--kv` → `DATABASE_PUBLIC_URL`):** группировка `charges` по
`(student_id, date)` сразу показала 5 идентичных пачек по 50 строк,
вставленных с разницей в секунды — отличило реальную гонку от гипотезы
«не фильтруется `deleted_at`» (та тоже была латентным багом, но 0 удалённых
оплат на проде, не эта причина).

**Фикс — два слоя, не один:**
1. `pg_advisory_xact_lock(hashtext('generate_monthly_charges'))` первой
   строкой функции — сериализует весь проход на уровне транзакции,
   закрывает конкретную гонку.
2. Частичный уникальный индекс `UNIQUE (student_id, date) WHERE
   description = 'Начисление за месяц'` — защита на уровне схемы, на
   случай если начисление когда-то будет вставлено в обход этой функции
   (ручной скрипт, будущий рефакторинг). Не общий `UNIQUE(student_id,
   date, description)` — `Charge` также значился для ручных корректировок
   (сейчас функция убрана целиком, см. ниже, но модель это не запрещает),
   которых в один день может быть несколько.

**Очистка данных:** удалены 200 лишних строк (по 4 из 5 копий на каждого
из 50 детей, оставлена самая ранняя по `id`) — единой транзакцией с
проверкой `COUNT(*) <> 1` перед `COMMIT`. Before/after по каждому ребёнку
показан владельцу до удаления. Июльские начисления (123 шт, 1 на ребёнка)
проверены отдельно — чистые, этот баг их не касался.

**Июльские начисления удалены отдельно (05.08).** Открытый вопрос выше
решён: родители в июле платили, но вне ИС (боевой отсчёт системы — с 1
августа). Все 123 строки `Charge` за июль (842 258.10 сом, org_id=4)
удалены прямым SQL после подтверждения владельцем — в системе нет UI-пути
для удаления начисления (ручная корректировка убрана целиком 04.07, см.
раздел выше). Проверено перед удалением: 8 июльских income-транзакций
(276.50 сом) — тестовые копеечные платежи с проверки Optima 14.07, к
реальным родительским оплатам отношения не имеют, не тронуты. Баланс
теперь считается только с августа.

## Гонка при создании ребёнка (05.08) — та же природа, что и гонка начислений

Отдельный от начислений инцидент: `/students/add` не имел никакой защиты от
повторного клика — 3 отдельных сабмита за 3 секунды (не одна параллельная
транзакция, а именно три последовательных запроса) задвоили/затроили
карточку одного ребёнка (Бопоева Акмаанай — 3 копии, Ташболотов и
Шахтыбеков — свои случаи). Реальный платёж Optima ушёл на PIN одной из
копий, начисление на «правильной» копии успело посчитаться раньше, чем
появился `Enrollment` — не увидело льготный тариф. Полная диагностика и
ручные фиксы конкретных детей — только в сессионном логе 05.08
(`context/summary.md`), в системный паттерн не годятся (разовая уборка).

**Системная защита — новый переиспользуемый хелпер**
`app/services/dedup_guard.py::acquire_submission_lock(db, scope, fingerprint)`
— тот же `pg_advisory_xact_lock`, что уже закрывает гонку начислений выше и
гонку `menu_day_save` (23.07), только вынесен в общую функцию, чтобы не
копировать `SELECT pg_advisory_xact_lock(...)` в каждый роут заново.
Применён в `/students/add` (лочит по объект+ФИО, внутри лока проверяет «не
заводили ли уже такого ребёнка за последние 10 секунд» — при совпадении
редиректит на существующую карточку вместо второй копии) и в
`/menu/dishes/new` (лочит по имени блюда — `get_or_create_dish()` и так
ищет точное совпадение, лок просто делает эту проверку безопасной при
одновременных запросах). Проверено вживую: 3 одновременных потока на одно
и то же имя — создаётся ровно одна запись.

**Осознанно не применено к** `/expenses/add`, `/warehouse/writeoff/add`,
поставщикам/ОС/услугам — там повтор одинаковой суммы/позиции за несколько
секунд может быть законным действием, не глюком; фингерпринт «то же имя за
N секунд» там был бы неверным по своей природе, не просто недоделанным.

**Плюс дополняющая клиентская защита** — глобальный обработчик в
`base.html` блокирует кнопку сабмита сразу по клику (через `e.submitter`,
не первую попавшуюся кнопку формы — на `expenses/confirm.html` их
несколько с разными `name=action`). Гасит саму причину инцидента
(усталый повторный клик), не требует переноса на другие роуты. Не
покрывает формы на `fetch()` (модалка создания товара, чипы в Меню) — у
них уже есть свои проверки.

## Разовые услуги — канцелярия и т.п. (25.08)

`Service.is_recurring` (default `True`) — второе измерение помимо
`is_tuition`. Обычные доп.услуги (проезд, секция) — ежемесячные,
подключаются чекбоксом (`StudentService`), начисляются
`generate_monthly_charges()`. Разовая услуга (`is_recurring=False`,
канцелярия — первый пример) — оплачивается раз в год наличными, не
подключается чекбоксом вообще, не трогается ежемесячным начислением.
Живёт в отдельной секции «Разовые услуги» на `/services/`, не смешана с
ежемесячными в одном списке.

**Отметка оплаты = начисление и оплата одним действием.** `POST
/services/{id}/pay` (student_id, amount, date) создаёт сразу `Charge` +
`Transaction(income, service_id, charge_id)` — гасят друг друга, баланс
ребёнка не меняется. Без этого разовый приход читался бы как чистая
переплата (см. «Баланс = Charge − Transaction» выше) — поймано advisor-
ревью до кода, `get_balances`/`get_balance`/`get_ledger` не делают
исключений для доходов без начисления.

**Наличные → сразу в подотчёт.** Та же оплата создаёт
`CashFunding(source_type='direct_cash', source_transaction_id=...)` —
получатель (`taken_by`/`accountable_user_id`) берётся из
`Organization.cash_recipient_user_id` (настройка на новой странице
`/settings/`, не роль в коде и не обязательно тот, кто нажал кнопку — в
жизни деньги физически попадают одному конкретному человеку, сейчас
Махабат). NULL → получателем становится тот, кто отметил оплату — новый
объект без кассира работает из коробки. Закрывает разрыв, о котором
предупреждал advisor при UX-развороте [[architecture/podotchet_module]]:
после разделения форм пополнения прямой «наличные без источника» стало
неоткуда взять — теперь единственный путь именно этот.

**Удаление — только с этой стороны, каскадом.** `POST
/services/payments/{transaction_id}/delete` мягко удаляет разом
Transaction + Charge + CashFunding (все три). `podotchet.delete_funding`
отдельно проверяет `source_transaction_id` и отказывает с понятным
сообщением, если запись создана отсюда — иначе удаление в подотчёте
оставило бы доход висеть в балансе ребёнка, а деньги тихо исчезли бы из
подотчёта. `Charge` получил `deleted_at` этой же миграцией (раньше не
имел — начисления были append-only) — `get_balances`/`get_balance`/
`get_ledger` теперь фильтруют его, как и `Transaction`.

**Счётчик «N из M» — живой, за учебный год.** `service_payments.
get_one_time_service_status()` считает заново при каждом обращении:
учебный год начинается 1 сентября (`academic_year_start`), знаменатель —
активные+замороженные дети объекта на сегодня. Без границы года счётчик
после первого сентября показывал бы «все уже заплатили» — оплаты за
позапрошлый год никуда не делись бы из суммы.

**Защита от двойного сабмита** — тот же `acquire_submission_lock`
(`dedup_guard.py`), что и `/students/add`: лок по
`service_id:student_id:date:amount`, внутри — проверка на дубль за
последние 10 секунд.

**Настройка кассира — отдельная страница `/settings/`, не довесок на
«Услуги».** Первая версия макета держала «Принимает наличные» прямо на
`/services/` — отклонено пользователем по тому же принципу, что
разделение форм подотчёта: настройка объекта не должна жить там, где её
не ждут. Остальные настройки объекта (`frozen_discount_percent`,
`sadik_portion_percent`, `legacy_tariff_*`) пока остаются на `/services/`
— перенос на `/settings/` сознательно отложен, не входит в объём этой
сессии.

## Известный риск — тарифы не сверены с Айжан/Мунарой напрямую

Механика подтверждена **Абдусаттаром** (13.07), но не самими Мунарой/Айжан
— это разговор, который тянется с 03.07 и до сих пор не случился. Прежде
чем показывать суммы долга кому-то как окончательный факт — свериться. Раз
теперь известна точная механика (база 8000 + скидка в сомах), сверку можно
сделать конкретно: «правда ли база 8000, и правильные ли суммы скидок у
конкретных детей» — не абстрактный вопрос «какие тарифы», как раньше.

# Подотчёт — архитектура и решения

> Спроектировано и реализовано 25.08.2026. Не задеплоено на прод (только
> локально, проверено вживую через dev-сервер + браузер).

## Зачем

Родители платят на счёт (Optima), но деньги регулярно снимаются на продукты,
зарплату и т.п. — до этой фичи не было механизма, кто снял, сколько, на что,
и отчитался ли. Реальный остаток на счету расходился с тем, что должно было
остаться, без возможности понять почему (прямой запрос владельца).

## Модель — два новых источника денег на руках

**`CashFunding`** — пополнение подотчёта, а не «снятие» (переименовано в
процессе — деньги приходят человеку в руки двумя разными путями):
- `source_type='withdrawal'` — сняли со счёта, учитывается в сверке остатка
- `source_type='direct_cash'` — наличные мимо банка (пример из разговора —
  канцелярский сбор с детей, ~3500 сом/год, собирается наличными руками; сам
  биллинг этого сбора **не реализован**, см. раздел «Отложено» ниже)

`organization_id` — чей это подотчёт (Школа/Сокулук/Кожомкул, все три реально
существуют как `Organization`, id 2/4/5). `taken_by`/`accountable_user_id` —
разные поля осознанно: Мунара может снять и передать Махабат, «кто отчитывается»
— не обязательно тот же человек, что физически снял. `source_organization_id`
(nullable) — только когда деньги физически из **другой** кассы (см. «Перетоки»).

**`AccountBalanceSnapshot`** — точка сверки: реальный остаток по счёту на дату,
введён вручную. Тот же паттерн, что `Supplier.opening_balance/opening_balance_date`
— расчётный остаток на любую дату = ближайшая точка ДО неё + приход − снятия
− прямые расходы **после** неё. Не пытается восстановить историю до первой
введённой точки.

**`Transaction.paid_directly`** (новая колонка, default `False`) — единственное
новое поле на форме расхода (Закуп/Сервис/чек/ФОТ/Ежемесячные). `False`
(умолчание, ничего не нажимать) — расход **сам** списывается с открытого
подотчёта того бизнеса, под которым проведён. `True` — оплата прошла напрямую
со счёта (перевод/карта), минуя наличные — тогда вычитается из остатка счёта
отдельно, подотчёт не трогает.

## Архитектурный разворот в процессе — от select к галочке

Первая версия плана: на каждом расходе — select «списать с чьего подотчёта».
**Отклонено after 3 раза одним и тем же вопросом от пользователя** — advisor
указал причину: ключ «кто ввёл запись» ≠ «чьи деньги потратил» (Мунара снимает
и отдаёт Махабат — Махабат вводит чек), а привязка по человеку на каждом
расходе — лишняя точка трения для нетехнического персонала. Правильный ключ —
**один открытый подотчёт на бизнес**, не на человека: расход списывается сам
по `organization_id`, который у Transaction и так уже есть. Единственное, что
остаётся выбирать вручную — редкое исключение (галочка «оплачено напрямую»).

Следствие: **не нужен `withdrawal_id` FK на Transaction, не нужен FIFO-выбор
конкретного пополнения** — баланс считается на лету суммой по организации
(`app/services/podotchet.py`, тот же приём, что `supplier_ledger.py`: пул
растёт пополнениями, тратится расходами, FIFO только для того, чтобы понять,
у КОГО из нескольких пополнителей что осталось «на руках» для отображения).

## Реальный баг, пойманный сквозным тестом до деплоя

`paid_directly` добавлен миграцией с `server_default='false'` — то есть
**все существующие** (исторические, тестовые) расходы в БД мгновенно
считались «из подотчёта». Первый же тест показал: свежесозданное снятие в
15 000 сом показывало `remaining=0` сразу после создания — потому что старые
расходы (введённые в процессе разработки, задолго до появления этой фичи)
«съедали» пул. Фикс — `PODOTCHET_START_DATE = 2026-08-25` (константа в
`podotchet.py`), фильтрует расходы, участвующие в списании пула, только с
этой даты — тот же приём, что `billing_cutoff`/`legacy_tariff` в других
модулях: чистый старт, не пытаемся развести реальные деньги задним числом.

**Урок:** при добавлении `server_default` булевой колонки, которая управляет
финансовым расчётом, проверять эффект на уже существующих строках ДО того,
как считать фичу готовой — не только на новых записях.

## Перетоки между бизнесами — справочно, не долг

Школа/Сокулук/Кожомкул — три реальных бизнеса, но учёт в системе полноценно
ведётся только для Сокулука (Optima, начисления). На практике деньги одного
покрывают расходы другого (например, Кожомкул одолжил наличными на часть
зарплаты Сокулука). Решено: **не строить формальный AR/AP-долг между
бизнесами** — пользователь прямо сказал «указать, что как переток получается»,
не «отследить возврат». `CashFunding.source_organization_id` — опциональное
поле именно на форме пополнения (не на каждом расходе), заполняется редко;
витрина `podotchet.get_cross_org_flows()` просто суммирует такие записи за
период и показывает `откуда → куда: сумма`.

## Доступ

`ALLOWED_ROLES = (owner, founder, staff, manager)` в `podotchet.py` — шире, чем
`/dashboard` (`owner, founder, staff`), **осознанно**: Мунара (role=`manager`)
иначе была бы заблокирована на главном экране этой же фичи — реальная дыра,
которая есть и в `/dashboard/unit-economics` (не трогали, не в скоупе).

`founder` (Айдай/Талас) — видят экран (прозрачность для собственников), но
**исключены из списков «снял/отчитывается»** (`User.role != "founder"` в
запросе) — по прямому запросу: «собственник бизнеса, не участвует в
операционке». Решение по роли, не по имени — Талас (та же роль) исключается
автоматически, без отдельного упоминания.

`business_orgs()` (все реальные бизнесы, Школа/Сокулук/Кожомkyл) — **не**
фильтруется через `get_accessible_orgs`/`PILOT_ORG_IDS` на форме пополнения:
Мунара пилотно ограничена только Сокулуком в остальной системе, но должна
мочь пометить снятие как «для Школы» — иначе перетоки нечем было бы завести.

## UX-разворот — разделение форм вместо одной универсальной (25.08, вторая половина сессии)

Первая реализованная форма пополнения смешивала в одной модалке три разных
по смыслу действия: снятие своего бизнеса / переток из чужого / ручной приход
наличных, с select «для какого бизнеса» и чекбоксом «деньги физически из
кассы другого бизнеса», раскрывающим доп.поля. Пользователь отверг это резко
и трижды подряд — не как денежную ошибку (advisor её не поймал бы, это не его
специализация), а как ошибку потока экрана: «должно быть всё там, где, как
должно быть, не смешивать». Урок сохранён в памяти как
[[feedback_ui_preview_before_build]] с уточнением — макет мало показать,
поток действий надо явно прогонять через отдельную UX-проверку, не полагаться
на advisor для этого класса ошибок.

**Итоговая модель — два независимых действия, без общего select:**
- **«Снять деньги»** (`POST /podotchet/withdraw`) — организация берётся из
  контекста страницы (org-select наверху, тот же, что везде в системе), не
  спрашивается в форме. Поле «Снял» тоже убрано — человек, открывший форму,
  и есть тот, кто физически снимает в подавляющем большинстве случаев;
  `taken_by` роутер подставляет сам (`user.id` из сессии). Остаётся только
  «Отчитывается» — единственное реальное решение на этой форме, раз снял и
  сразу передал другому.
- **«Одолжили у другого бизнеса»** (`POST /podotchet/borrow`) — зеркальная
  форма: получатель всегда текущий объект, выбирается только «Откуда»
  (`source_organization_id`, обязателен, не равен текущему). Пишется как
  `source_type='direct_cash'` — деньги физически никогда не были на счету
  получателя, поэтому не должны уменьшать его расчётный остаток по банку
  (`get_expected_balance` считает `withdrawals` только по `source_type=
  'withdrawal'`).
- Старый единый `POST /podotchet/fund` и его select/чекбокс удалены целиком.

**Защита от нелистового объекта** (найдена advisor-ревью): owner/founder/
manager видят в org-select наверху ВСЕ узлы дерева орг, включая родительские
(«Жемчужина» id=1, «Садики» id=3), не только реальные бизнесы — `resolve_org`
может на них приземлиться. Снятие, записанное на такой узел, создаёт пул,
который ни один расход никогда не спишет (Transaction.organization_id всегда
лист). `_resolve_business_org()` в роутере проверяет входит ли org_id формы в
`_business_orgs()` (лист дерева) — иначе отказ с понятным сообщением, а не
тихая запись. GET `/podotchet/` тоже редиректит с родительского узла на
ближайший доступный бизнес при заходе на страницу.

**Мягкое удаление** — раньше пополнения можно было только создавать, опечатка
в сумме портила баланс навсегда без возможности исправить. `POST
/podotchet/fund/{id}/delete` — тот же паттерн, что `SupplierPayment`/`WriteOff`
(`deleted_at = func.now()`, все запросы в `podotchet.py` его уже фильтровали).

**Известный, осознанный разрыв на время сессии**: между переходом на новую
модель и запуском модуля «Сборы» — прямого прихода наличных мимо банка без
привязки к другому бизнесу стало негде завести (раньше это была кнопка
«Наличными собрано» в единой форме). Канцелярский сбор, вносимый наличными
— именно этот случай. Найдено advisor-ревью до переноса в код, разрыв
закрывается тем же модулем «Сборы» позже в этой же сессии (см. ниже) —
не отдельная временная заглушка.

## Отложено — канцелярские (следующая сессия)

Канцелярский сбор (~3500 сом/ребёнок/год, наличными) упомянут как пример
`source_type='direct_cash'`, но **сам сбор как биллинг не реализован**:
- Нет `Service` для этого сбора
- Нет пути ручного прихода (весь `income.py` сейчас — только чтение; создаёт
  `Transaction(type=income)` единственно `optima.py`, банк)
- Значит «кто из детей заплатил / кто должен» — не отслеживается индивидуально

После UX-разворота (см. выше) ручного пути завести `direct_cash` без
`source_organization_id` в UI подотчёта больше нет — единственный способ
записать наличный приход, минующий банк, теперь через модуль «Сборы»
(отметка оплаты по ребёнку сама создаёт `CashFunding(source_type=
'direct_cash')`). Полноценный биллинг по ребёнку — отдельная задача, с
собственным макетом до кода (см. [[feedback_ui_preview_before_build]] в
памяти), уже спроектирован (`sbory-preview.html`), реализация следующим
шагом в этой же сессии.
